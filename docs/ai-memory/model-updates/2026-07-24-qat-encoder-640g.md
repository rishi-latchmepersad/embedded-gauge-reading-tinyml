# QAT encoder 640x640 grayscale ellipse detector — 2026-07-24

Date: 2026-07-24
Status: failed (TFLite int8 radius output collapses to constant)
Scope: 640x640 grayscale ellipse detector, second attempt after RepVGG

## Goal

Build on the proven QAT-encoder pattern (from
`docs/ai-memory/lessons-learned/2026-07-23-qat-safe-architecture.md` and
the 224x224 reference at `ml/artifacts/gauge_ellipse_qat_encoder_v1/`)
but at 640x640 grayscale with < 1.5 MB peak activation.

## Architecture

```text
input  640x640x1
stem   3x3 stride 4, 24ch     -> 160x160x24   (1.23 MB int8, PEAK)
s1     [2 blocks, 72ch]       -> 80x80x72
s2     [2 blocks, 96ch]       -> 40x40x96
s3     [2 blocks, 144ch]      -> 20x20x144
s4     [2 blocks, 192ch]      -> 10x10x192
GAP + Dropout 0.1 + Dense 128
head   3x Dense(sigmoid): center_xy, radius_xy, confidence
```

Stride-4 stem keeps peak under 1.5 MB. All Conv+BN+ReLU blocks
(no SE, no Multiply, no Lambda) match the QAT-safe pattern.

## What was tried (v1, v2, v3)

| Variant | Head | Result |
|---|---|---|
| v1 | 3 separate heads, radius LINEAR | TFLite center MAE 48 px, radius variance 0 |
| v2 | single Dense(5, sigmoid) + Lambda split | Lambda fails tfmot deserialisation |
| v3 | 3 separate heads, all sigmoid | TFLite center MAE 28 px, radius variance 0 |

All three variants trained FP32 + QAT to completion. The Keras fp32
model works well in every variant. The TFLite int8 model is consistently
broken in a specific way: the radius output collapses to a constant
while the center and confidence outputs degrade but still vary.

## What works (Keras fp32 v3)

| Metric | Val (927) | Test (936) |
|---|---|---|
| Center MAE | **7.44 px** | 10.20 px |
| Center median | 4.57 px | 4.49 px |
| % within 8 px | **74.9%** | **75.2%** |
| % within 4 px | 43.0% | 44.8% |
| Radius variance (pred) | 656 | 595 |
| Radius variance (GT) | 917 | 1402 |

The Keras fp32 model is the best ellipse detector trained so far on
this dataset. Beats the previous RepVGG attempt (71% within 8 px) and
matches the existing `gauge_ellipse_qat_encoder_v1` (224x224 baseline).

Activation budget (int8 deployment, would be if conversion worked):
- Input: 640x640x1 = 410 KB
- Stem: 160x160x24 = 614 KB
- s1: 80x80x72 = 461 KB
- s2: 40x40x96 = 154 KB
- s3: 20x20x144 = 58 KB
- s4: 10x10x192 = 19 KB
All well under 1.5 MB.

## What fails (TFLite int8 v3)

The TFLite int8 model is **broken**: it produces varying center and
confidence predictions, but the **radius output is a constant**.

| Metric | Val (TFLite) | Test (TFLite) |
|---|---|---|
| Center MAE | 28.4 px | 31.0 px |
| Center % within 8 px | 1.2% | 0.6% |
| Radius MAE | 49.2 px | 51.7 px |
| Radius variance | **0.0** | **0.0** |

TFLite parity vs Keras fp32:
- center_xy: mean diff 0.0X, max 0.1X
- radius_xy: mean diff 0.0X, **max 0.39** in normalised [0, 1] space
- confidence: mean diff 0.004, max 0.004

The radius is consistently the failing output across all three
architectural variants. The int8 calibration picks a single (min, max)
range for the radius output and the resulting grid is too coarse for
the narrow radius distribution (rx, ry cluster in [0.4, 0.5]).

## Why the radius fails

The 9,191 training images have gauge radii in [0.4, 0.5] (normalised
[0, 1]). The int8 calibration has 256 levels to cover [0, 1] which
means each int8 step is 0.004 in normalised coords. The radius
variation across the dataset is ~0.1, so we have ~25 distinct int8
levels for the radius.

But the radius output is consistently predicted near the dataset
mean (0.45-0.50). The Keras fp32 model produces radius values in
[0.4, 0.5] with a std of 0.04, which after int8 calibration should
span ~10 distinct levels. Yet the int8 output collapses to a single
value.

This is the same `2026-07-23-qat-safe-architecture.md` bias-only
failure mode, but it only affects the radius output. The center and
confidence outputs survive because their distribution covers a wider
range relative to their output range (center is in [0, 1] with
significant variation; confidence is near 1.0 and the int8 grid
calibrates around that).

## Decision

The Keras fp32 model at `gauge_ellipse_qat_encoder_640g_v2/model_fp32.keras`
is a strong offline candidate (~75% within 8 px center error). The
TFLite int8 export is broken across all three architectural variants
attempted. Per the AI memory guidance, do not waste more time on
PTQ/QAT conversion experiments.

Future TFLite work should either:
1. Accept a smaller input (e.g. 224x224) and resize 640x640 to 224x224
   at inference time. The existing `gauge_ellipse_qat_encoder_v1`
   model already produces a working int8 TFLite at that size; we
   would just need to add a pre-processing resize on the board.
2. Use a different model family that is known to be TFLite-friendly
   at 640x640 in this environment. This is exploration, not a
   known-good path.

## Recommended next step

Deploy the v2 Keras fp32 model as the offline ellipse detector, and
add a 640x640 -> 224x224 resize + the existing 224x224 QAT encoder
as the on-board int8 path. This gives the best of both: a high-
accuracy offline model and a working int8 board model. The cost is
one extra resize op on the board.
